# Findomain 11.0.0-beta.2

Second beta of Findomain 11. This page lists only what changed since the
first beta; the full picture of the 11 series, including its breaking
changes, is in the notes for
[11.0.0-beta.1](https://github.com/Findomain/Findomain/releases/tag/11.0.0-beta.1).

Pre-release: not marked as the latest release, not pushed to Docker Hub, not
picked up by distribution packages. Grab a binary from the assets below or
build from the tag:

```
git clone --branch 11.0.0-beta.2 https://github.com/Findomain/Findomain
cd Findomain && cargo build --release
```

## Changes since 11.0.0-beta.1

### nuclei findings are reported as they appear

nuclei writes one finding per line as it goes, but the first beta read its
output only once the process exited: an hours-long scan showed nothing until
the end, and one stopped at its deadline lost everything it had found. Each
finding is now printed the moment nuclei reports it.

In monitoring mode, every actionable finding (low and above) is also posted
to the webhooks on its own message as it arrives, instead of reaching the
emailed report only. Informational findings stay out of the chat, and keep
going to stdout and the email.

- `smart_alerts_webhook` (configuration file or `FINDOMAIN_SMART_ALERTS_WEBHOOK`)
  routes findings to a dedicated Discord or Slack channel, away from the
  daily subdomain traffic. It is the key findomain-plus used, so an existing
  configuration keeps working. Empty sends them to the regular webhooks.
- `--nuclei-timeout` and `nuclei_timeout` now default to 0, no limit. When
  set, nuclei is stopped at the deadline and whatever it reported until then
  is kept and returned, with a note on stderr. The first beta defaulted to
  5400 seconds and discarded the findings on timeout; if you relied on that
  ceiling, set it explicitly.
- The closing monitoring alert now covers new subdomains only, since the
  findings were already sent one by one.

### Webhook rate limits are waited out (#327)

A first run with a thousand new subdomains is fourteen Discord messages sent
back to back, and Discord allows five per two seconds. The sixth got a 429,
the chunk was dropped, and because the results had already been stored those
subdomains were never alerted again.

A 429 is now waited out for exactly the `Retry-After` the service sends, for
as long as it keeps sending one, with a line on stderr per wait unless
`--quiet`. `--webhook-max-wait` and `webhook_max_wait` put an optional ceiling
on the total wait per message; 0, the default, means none.

### `--list-keys` (#64)

Prints every source that takes an API key, the configuration key and the
environment variable that set it, and whether one is configured: how many,
never the value. The status also says what the absence means for that
source, skipped entirely or run on the free quota.

### Docker image for amd64 and arm64

The published image was amd64 only. From the next stable release it is
built for `linux/amd64` and `linux/arm64` from the same static binaries the
release ships, and tagged both `latest` and by version. Nothing is
downloaded while the image builds, so it always matches its release. Images
are only published for stable tags, so this beta does not push one.

### New asset: `findomain-aarch64-musl.zip`

A static aarch64 build, the one the arm64 image is made from. It also suits
Alpine and Termux on arm64, where the glibc build in `findomain-aarch64.zip`
does not run. That one stays as it was for everything else. Nine assets in
total now.

### Fixed

- The process runner waited on a tool's output pipe even after the tool had
  exited or been killed. A helper the tool started could keep that pipe open
  and hold the whole run; it no longer does.

## Requirements

Unchanged: nmap for `--pscan`, nuclei for `--nuclei`, ffuf for `--ffuf`, and
Chromium or Chrome for `--screenshots`, each on `PATH` only if you use it.
